# Week 11 실습

## 오늘 한 것

이번 주에는 내가 만든 파이썬 중간 프로젝트를 **PyInstaller를 사용해서 Windows 실행 파일(.exe)로 만드는 과정**을 실습했다. 지금까지는 Thonny에서 `F5`로 실행해서 게임이 잘 돌아가는지만 확인했는데, 이번 수업에서는 내가 만든 게임을 다른 사람의 컴퓨터에서도 실행할 수 있도록 배포 가능한 형태로 만드는 방법을 배웠다.

먼저 터미널에서 `pyinstaller --version` 명령어를 입력해 PyInstaller가 설치되어 있는지 확인했다. 버전 번호가 출력되면 설치가 되어 있는 상태이고, 설치되어 있지 않다면 `pip install pyinstaller`를 통해 설치해야 한다는 것을 알게 되었다. 이후 중간 프로젝트 폴더로 이동해서 `pyinstaller game.py` 명령어로 첫 빌드를 진행했다. 빌드가 끝나면 프로젝트 폴더 안에 `build`, `dist`, `game.spec` 파일이 생성된다는 것도 확인했다. 여기서 `build` 폴더는 임시 파일에 가깝고, 실제 실행 파일은 `dist` 폴더 안에서 확인할 수 있었다.

첫 빌드 후에는 `dist/game/game.exe`를 직접 더블클릭해서 실행 여부를 확인했다. 이때 실행 자체가 되는지 확인하는 것이 우선이고, 이미지나 사운드가 정상적으로 나오는지도 함께 확인해야 한다는 것을 배웠다. 만약 실행은 되지만 이미지나 사운드가 보이지 않는다면 단순 코드 문제가 아니라 **경로 문제**일 가능성이 높다는 점이 중요했다.

그다음에는 절대경로와 상대경로의 차이를 학습했다. 절대경로는 `C:/Users/.../project/assets/player.png`처럼 컴퓨터 안의 전체 주소를 적는 방식이고, 상대경로는 `assets/player.png`처럼 현재 위치를 기준으로 파일을 찾는 방식이다. 개발 중에는 상대경로가 잘 동작하는 경우가 많지만, 빌드 후에는 실행 환경이 달라지기 때문에 상대경로만 믿으면 문제가 생길 수 있다는 것을 알게 되었다.

특히 PyInstaller의 `--onefile` 옵션을 사용하면 실행 파일이 내부적으로 임시 폴더에 압축 해제되어 실행된다는 점이 인상 깊었다. 개발 중 Thonny에서 실행할 때는 현재 작업 디렉터리와 `game.py`가 있는 폴더가 같아서 `assets/player.png`를 잘 찾을 수 있다. 하지만 `.exe`로 만든 뒤 실행하면 실제 코드가 실행되는 위치와 사용자가 더블클릭한 위치가 달라질 수 있어 파일을 찾지 못하는 문제가 생긴다.

이 문제를 해결하기 위해 `resource_path()` 함수를 작성했다. 이 함수는 개발 중일 때와 빌드 후일 때를 구분해서 올바른 파일 경로를 만들어 주는 역할을 한다. 코드에서는 `sys._MEIPASS`가 있으면 PyInstaller로 빌드된 실행 파일 안에서 실행 중이라고 판단하고, 없으면 일반 개발 환경이라고 판단한다. 이후 `os.path.join()`을 사용해서 이미지, 사운드, 폰트 파일의 정확한 경로를 만들어 준다.

또한 게임 코드에서 파일을 불러오는 부분을 모두 수정해야 한다는 것도 배웠다. 예를 들어 `pygame.image.load("assets/player.png")`처럼 직접 경로를 쓰던 부분을 `pygame.image.load(resource_path("assets/player.png"))`로 바꾸어야 한다. 사운드 파일도 `pygame.mixer.Sound(resource_path("sounds/shoot.wav"))`처럼 바꾸고, 폰트 파일도 `pygame.font.Font(resource_path("fonts/myfont.ttf"), 24)`처럼 수정해야 한다. 다만 `pygame.font.SysFont()`는 시스템 폰트를 사용하는 것이므로 경로 수정이 필요 없다는 점도 알게 되었다.

이후에는 옵션을 붙여서 다시 빌드하는 방법을 실습했다. 기본적으로는 `pyinstaller --onefile game.py`를 사용해 실행 파일 하나로 묶을 수 있고, 배포용으로 터미널 창을 숨기려면 `--windowed` 옵션을 추가할 수 있다. 그리고 이미지나 사운드 같은 에셋 폴더를 실행 파일에 포함하려면 `--add-data "assets;assets"` 옵션을 사용해야 한다. 최종적으로는 `--name=MyGame` 옵션을 붙여 실행 파일 이름도 지정할 수 있었다.

마지막으로 오류 대응 방법을 학습했다. 실행 자체가 안 되면 모듈 누락을 의심하고, 이미지나 사운드가 나오지 않으면 `resource_path()` 적용 여부와 `--add-data` 옵션을 확인해야 한다. 또 `--windowed` 옵션을 켜면 오류 메시지가 터미널에 보이지 않기 때문에, 디버깅할 때는 `--windowed`를 빼고 다시 빌드해서 터미널에 나타나는 오류 메시지를 확인해야 한다는 점을 배웠다. 이 과정에서 프로그램을 완성한다는 것은 단순히 코드를 작성하는 것뿐만 아니라, 오류가 생겼을 때 원인을 분석하고 해결할 수 있어야 한다는 것을 느꼈다.

## resource_path() 를 써야 하는 이유

`resource_path()`를 써야 하는 가장 큰 이유는 **개발 중 실행 환경과 빌드 후 실행 환경이 다르기 때문**이다. Thonny에서 `F5`로 실행할 때는 보통 `game.py`가 있는 프로젝트 폴더가 현재 작업 디렉터리로 잡힌다. 그래서 `pygame.image.load("assets/player.png")`처럼 상대경로를 사용해도 `project/assets/player.png`를 정상적으로 찾을 수 있다. 이때는 코드와 에셋 폴더의 위치가 맞아떨어지기 때문에 별문제가 없는 것처럼 보인다.

하지만 PyInstaller로 `.exe` 파일을 만들면 상황이 달라진다. 특히 `--onefile` 옵션을 사용하면 실행 파일 하나 안에 코드와 필요한 파일들이 묶이고, 실행할 때는 내부 파일들이 임시 폴더에 풀린다. 이때 PyInstaller는 그 임시 폴더 경로를 `sys._MEIPASS`라는 변수에 저장한다. 따라서 빌드된 실행 파일에서는 단순히 현재 폴더 기준으로 `assets/player.png`를 찾으면 실제 파일 위치와 맞지 않아 오류가 발생할 수 있다.

예를 들어 개발 중에는 `C:/Users/.../project/assets/player.png` 위치에 파일이 있어서 잘 실행될 수 있다. 하지만 빌드 후에는 사용자가 바탕화면에서 `.exe`를 실행할 수도 있고, 실제 프로그램 내부 파일은 `AppData/Temp/_MEIxxxxx` 같은 임시 폴더에 풀릴 수도 있다. 이 상태에서 상대경로만 사용하면 프로그램은 잘못된 위치에서 `assets` 폴더를 찾게 되고, 결국 이미지나 사운드가 보이지 않는 문제가 생긴다.

그래서 `resource_path()` 함수가 필요하다. 이 함수는 먼저 `sys._MEIPASS`가 있는지 확인한다. 만약 `sys._MEIPASS`가 있다면 PyInstaller로 빌드된 실행 파일 안에서 실행 중이라는 뜻이므로, 임시 폴더를 기준 경로로 사용한다. 반대로 `sys._MEIPASS`가 없다면 아직 개발 중인 일반 파이썬 실행 환경이므로, `__file__`을 기준으로 현재 `.py` 파일이 있는 폴더를 사용한다.

결국 `resource_path()`는 개발 중에도, 빌드 후에도 같은 코드가 안정적으로 파일을 찾을 수 있게 해 주는 함수이다. 이미지, 사운드, 폰트처럼 외부 파일을 불러오는 게임 프로젝트에서는 이 함수가 매우 중요하다. 이번 실습을 통해 게임이 내 컴퓨터에서만 실행되는 것이 아니라, 다른 환경에서도 정상적으로 실행되도록 만들려면 파일 경로를 정확하게 처리해야 한다는 것을 배웠다.

이번 내용을 통해 나는 평소에 아무 생각 없이 사용하던 상대경로가 사실은 실행 환경에 크게 영향을 받는다는 것을 알게 되었다. 앞으로 프로젝트를 만들 때는 처음부터 `assets`, `sounds`, `fonts`처럼 폴더 구조를 정리하고, 파일을 불러올 때는 `resource_path()`를 적용하는 습관을 들여야겠다고 느꼈다. 그래야 나중에 `.exe`로 빌드할 때 이미지가 안 나오거나 사운드가 재생되지 않는 문제를 줄일 수 있을 것 같다.

## 빌드 명령어

오늘 실습에서 사용하거나 정리한 빌드 명령어는 다음과 같다.

```bash
pyinstaller --version
```

PyInstaller가 설치되어 있는지 확인하는 명령어이다. 버전 번호가 출력되면 설치가 완료된 상태이다.

```bash
pip install pyinstaller
```

PyInstaller가 설치되어 있지 않을 때 사용하는 설치 명령어이다.

```bash
pyinstaller game.py
```

가장 기본적인 빌드 명령어이다. 별도의 옵션 없이 실행 파일을 만드는 첫 단계에서 사용할 수 있다.

```bash
pyinstaller --onefile game.py
```

여러 파일로 나뉘어 생성되는 결과물을 실행 파일 하나로 묶기 위한 명령어이다.

```bash
pyinstaller --onefile --windowed game.py
```

실행 파일을 하나로 묶고, 실행할 때 터미널 창이 뜨지 않게 만드는 명령어이다. 게임처럼 사용자가 콘솔 창을 볼 필요가 없는 프로그램을 배포할 때 사용할 수 있다.

```bash
pyinstaller --onefile --windowed --add-data "assets;assets" --name=MyGame game.py
```

실행 파일 하나로 묶고, 터미널 창을 숨기며, `assets` 폴더를 실행 파일 안에 포함하고, 최종 실행 파일 이름을 `MyGame`으로 지정하는 명령어이다. Windows에서는 `--add-data` 옵션에서 원본 폴더와 번들 내부 경로를 세미콜론`;`으로 구분한다.

```bash
pyinstaller --onefile --add-data "assets;assets" --name=MyGame game.py
```

디버깅할 때 사용할 수 있는 명령어이다. `--windowed` 옵션을 제거했기 때문에 실행 중 오류가 발생하면 터미널 창에서 오류 메시지를 확인할 수 있다.

```bash
pyinstaller game.spec
```

옵션이 많아졌을 때 `.spec` 파일을 수정한 뒤 다시 빌드할 때 사용하는 명령어이다. 반복 빌드가 많을 경우 매번 긴 명령어를 입력하지 않아도 되어 편리하다.

## AI 활용 내역

이번 실습 내용을 정리하면서 AI를 활용해 11주차 수업 자료의 핵심 내용을 다시 정리했다. 특히 PyInstaller 빌드 과정, 상대경로와 절대경로의 차이, `sys._MEIPASS`와 `resource_path()`의 역할, `--add-data` 옵션의 의미, 오류 대응 방법을 이해하기 쉽게 풀어서 정리하는 데 도움을 받았다.

AI를 사용할 때 단순히 답을 복사하는 방식이 아니라, 수업 자료에 나온 내용을 바탕으로 내가 이해한 흐름에 맞게 다시 정리했다. 예를 들어 `resource_path()`를 써야 하는 이유는 “빌드 후에는 경로가 달라지기 때문”이라는 식으로만 외우는 것이 아니라, 개발 중에는 `game.py`가 있는 폴더를 기준으로 실행되고, 빌드 후에는 PyInstaller가 임시 폴더에 파일을 풀어서 실행한다는 구조까지 이해하려고 했다.

또한 빌드 명령어를 정리할 때도 AI를 활용해 각 옵션이 어떤 역할을 하는지 문장으로 설명했다. `--onefile`, `--windowed`, `--add-data`, `--name` 옵션을 각각 구분해서 정리하면서, 단순히 명령어를 외우기보다 실제 프로젝트를 배포할 때 어떤 상황에서 어떤 옵션을 사용해야 하는지 생각해 볼 수 있었다.

이번 AI 활용을 통해 수업 내용을 더 길고 자세하게 정리할 수 있었지만, 최종적으로는 내가 직접 이해한 내용을 바탕으로 수정하는 것이 중요하다고 느꼈다. 앞으로도 AI를 사용할 때는 과제를 대신 작성하게 하는 용도보다는, 내가 배운 내용을 다시 설명해 보고 부족한 부분을 보완하는 도구로 활용해야겠다고 생각했다.

## 학습성찰

이번 11주차 실습을 통해 파이썬 프로젝트를 실제 실행 파일로 만드는 과정이 생각보다 단순하지 않다는 것을 알게 되었다. 이전까지는 코드가 실행되면 프로젝트가 거의 완성된 것이라고 생각했지만, 이번 수업을 통해 다른 사람이 실행할 수 있는 형태로 만드는 과정까지 포함해야 진짜 완성에 가까워진다는 것을 느꼈다.

특히 가장 중요하게 느낀 부분은 경로 처리였다. 개발 중에는 이미지와 사운드가 정상적으로 나오기 때문에 문제가 없다고 생각하기 쉽지만, `.exe`로 빌드한 뒤에는 실행 환경이 달라지면서 같은 코드가 다르게 동작할 수 있다는 점이 새로웠다. 이 내용을 배우면서 프로그램은 내가 만든 환경에서만 잘 돌아가는 것이 아니라, 사용자가 어떤 위치에서 실행하더라도 안정적으로 작동해야 한다는 것을 알게 되었다.

또한 오류를 해결하는 태도도 중요하다고 느꼈다. 빌드 후 이미지가 안 나오거나 실행이 안 되면 당황할 수 있지만, 이번 수업에서 배운 것처럼 오류 유형을 나누어 생각하면 원인을 찾기 쉬워진다. 이미지나 사운드가 없으면 경로 문제를 먼저 확인하고, 실행 자체가 안 되면 모듈 누락을 의심하며, 오류 메시지가 보이지 않으면 `--windowed`를 빼고 다시 실행해 보면 된다. 이렇게 문제를 단계적으로 확인하는 방식이 실제 개발에서 중요하다고 생각했다.

이번 실습을 바탕으로 앞으로 기말 프로젝트를 진행할 때는 처음부터 배포를 고려해서 작업해야겠다고 느꼈다. 파일을 아무 곳에나 두지 않고 `assets`, `sounds`, `fonts`처럼 폴더 구조를 정리하고, 모든 외부 파일 경로에는 `resource_path()`를 적용할 것이다. 또한 최종 제출 전에는 Thonny에서 실행 확인을 하고, PyInstaller로 빌드한 뒤, `dist` 폴더의 실행 파일을 직접 실행해 보고, 가능하면 다른 위치에서도 실행해 볼 계획이다.

이번 수업은 단순히 PyInstaller 명령어를 배우는 시간이 아니라, 내가 만든 프로젝트를 사용자에게 전달 가능한 형태로 완성하는 과정을 배우는 시간이었다. 앞으로는 “내 컴퓨터에서 실행된다”에서 끝내지 않고, “다른 환경에서도 실행된다”까지 확인하는 습관을 가져야겠다고 느꼈다.
